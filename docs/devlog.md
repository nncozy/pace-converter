### [Tech] VDOTの計算を calc.js に切り出してテストを付けた
- 動機は「間違えても画面が壊れない」こと。トレーニングペースがズレても、それらしい数字が出るだけで実際の練習に影響が出る。正しさの根拠がコメントに書かれた手計算の数字だけ、という状態だった。
- DOMにもlocalStorageにも触れない純粋計算だけを `js/calc.js` に移し、Nodeから直接呼べるようにした。`js/app.js` は22行追加/110行削除の純粋な抽出でロジックは無変更。
- 期待値には、コメントとREADMEが「確認済み」と書いていた換算表の実測値をそのまま置いた（VDOT50で E 5'07" / M 4'25" / T 4'15" / I 3'54" / R 3'41"、5km 19'56"、フル 3:10:40、サブ4≈VDOT37.9、サブ3≈VDOT53.5）。
- ゾーンの `pct`（0.70/0.84/0.88/0.98/1.05）も calc.js に移した。app.js の `TRAINING_ZONES` に置いたままだとテストが本番の値に届かず、テスト用に同じ数字を書き写すことになる。`T: 0.88` を `0.89` に変えると2件落ちることを実際に確認してから確定した。
- 「テストを書く」より「テストが届く場所に値を移す」方が本質だった回。

### [Ops] Tailwind CDNは測ったうえで、あえて変えなかった
- `https://cdn.tailwindcss.com` は **407KB（gzip 123KB）のJS** を落としてブラウザ内でCSSコンパイラを動かす仕組み。そこから生成されるこのアプリのCSSは実測 **24KB** だった（実行中のページから `<style>` の中身を測って確認）。
- 生成済みCSSに変えれば、初回オフラインで崩れない・スタイルが当たるまでの待ちが消える・存在しないクラス名（過去に `w-4.5` でアイコンが見えないバグを出している）が生成時に露見する、という3つが取れる。
- それでも見送った理由: `npx tailwindcss` を叩き直す作業が毎回増えるから。**`?v=N` の手作業を1つ減らした直後に、忘れると同じように静かに壊れる手作業を1つ増やすのは割に合わない**。測定値ごと `BACKLOG.md` に「検討中（要判断）」として残した。
- 本人にも「よくわからない」と言われたので、工場を送りつける方式 vs 完成品を送る方式、という説明に置き換えた。

## 2026-10-08

### [Product] 全体レビューをサブエージェント4体＋実機操作でやったら、テストで固めた値そのものが間違っていた
- 観点を「文言」「コードの正しさ」「UI/UX・アクセシビリティ」「競合・プロダクト」の4つに分けてサブエージェントに並列で投げ、その間に自分はブラウザのスマホ幅で実際に触った。重い指摘は自分でも再現してから採用した。
- 一番痛かったのは **Mペースが速すぎる** 件。`ZONE_PCT.M = 0.84` 固定のせいで、VDOT50 で M=4'25"/km なのに、同じ画面のポテンシャルタブのフル予想は 4'31"/km。Daniels表の M も 4'31"。遅い層ほどズレが広がり、VDOT30 では14秒/km速い（サブ4狙いの人がハーフのペースでフルに入ることになる）。
- しかも 9/14 に「換算表の実測値」として `M 4'25"` をテストの期待値に置いていた（cf92162）。**テストで固定したことで、誤りが「確認済み」の顔をして守られていた**。テストは「値を変えたら気づける」だけで、「値が正しい」ことは保証しない。期待値の出典を1行ずつ確かめていなかったのが原因。
- 実機で見つけたもの: ペース欄の「分」は2桁で自動で秒へ移る仕様なのに、ランナーのペースはほぼ1桁分。「4→3→0」と打つと 43'0"/km になる。作者本人は無意識に「4」→秒をタップ、で回避していたはず。
- もう1つ: 10000m に 41:23 と入れたあと、ペース欄をタップして離れるだけで 41:20 に書き換わる。フォーカスアウトで整数秒のペースから全体を引き直しているため。「触っただけで入力が変わる」は信頼を一番削る種類のバグ。
- ほかの主な指摘: ライトモードのヒーローは白文字×黄緑で約2.3〜3.1:1（屋外で一番重要な数字が一番読みにくい）、「ms」欄の中身は実は1/100秒、VDOTレベル目安の「48〜58はサブ3」が計算（VDOT48→フル3:17）と合わない、VDOTの入力距離にハーフ/フルがない、ペースがリロードで消える、I/Rの400mタイムが出ない、title/h1/計装がない。
- 競合調査では「どの距離からでも双方向に同期」はほぼ唯一。一方で周回累積表・URL共有・早見表は他所にあってここに無い。9/14 の「中心用途のトラック周りが一番薄い」という発見と同じ結論にもう一度たどり着いた。
- 教訓: 単一視点のレビューだと「動くし、テストも通る」で止まる。観点を割って並列で見て、最後に実機で再現する、の組み合わせが効いた。

### [Tech] レビュー指摘を直していったら「表示の根拠と数値を同じ場所から出す」話が2回出てきた
- Mペースは %VO2max 84% 固定をやめ、予想フルマラソンタイム÷42.195 から出すようにした（28825c3）。これで「Mペース＝ポテンシャルタイムのフルのペース」がどのVDOTでも成り立つ。テストも「換算表の値」ではなく「この2つが一致すること」を確かめる形を足した。誤った期待値を固定していた 9/14 のテストは 4'25"→4'31" に直した。
- VDOTレベル目安も同じ構図だった。「48〜58はサブ3」と書きながら、境界の数字は手で置いていたので文言と計算がずれていた。境界をフルのタイム（4:45/4:00/3:30/3:00/2:30/2:15）で定義し、VDOTは `vdotFromPerformance` で逆算する形にした（4f928da）。説明文と境界が同じタイムから出ていれば、片方だけ直してずれることがそもそも起きない。
- 教訓: 「数字」と「その数字を説明する文言」を別々に手で書くと、いつか必ずずれる。片方をもう片方から計算で出す。

### [UX] 「触っただけで値が変わる」を直したら、空欄の扱いで2回つまずいた
- 原因はフォーカスアウトのたびに表示値から再計算していたこと。ペース欄だけかと思ったら、計算結果のカードに触れて離れるだけでも同じことが起きていた（そこが基準になり、1/100秒の丸め分だけ全体がずれる）。「フォーカス後に実際に打ち込んだか」のフラグを立て、立っているときだけ再計算する形にした（a9d7a58）。
- 手戻り1: これで自動で送られてきた秒欄に何も打たずに離れると、空欄が `--` のまま残るようになった。値（0扱い）は変えずに、見た目だけ `00` にそろえる処理を足した。
- 手戻り2: 「ペース欄を両方消したら未入力に戻す」を空文字の判定で書いたら効かなかった。秒欄は離れた時点で `00` に整形されるので、両方が空になる瞬間がない。「0'00" はペースとして意味がない」という値での判定に変えて解決。
- ついでに「分」は2〜9の1桁で秒へ送るようにした。1と0だけは10分台・05のように続く可能性があるので2桁目を待つ。20分/km以上はペース欄からは打てなくなるが、1000mのカードから入れられるので割り切った。

### [UX] ライトモードは「グラデーションを暗くする」より「文字を黒くする」を選んだ
- 白文字×lime-600→green-500 は 2.1〜3.1:1。候補を2つ計算した。グラデーションを lime-700→green-700 に暗くすると白文字は5:1になるが、面が重くなる。黒文字にすると、今の明るい面のまま入力欄の窪み込みで5.4〜7.1:1。
- ダークモードはもともと「黄緑の面に黒い数字」だったので、黒文字にすれば両テーマで同じ見た目になる。こちらを採用（24248e9）。ヘッダーのペース表示・「基準」バッジ・ゾーンの丸アイコンも同じ組み合わせだったのでそろえた。

### [Tech] 余談：検証中に古いJS/CSSを掴まされ続けた
- Service Worker の precache が HTTP キャッシュ経由で入るので、ファイルを直しても古い版が返ってくる。SWの登録解除＋キャッシュ削除＋`fetch(url, {cache:'reload'})` でも、CSSだけ古いまま残ることがあった。最終的には `<link>` の href に `?dev=時刻` を付け替えて確認した。本番は `npm run version:bump`（v22）で回避している。
- もう1つの自爆: テスト用の `el?.click() ?? fallback.click()` が、`click()` が undefined を返すせいで毎回フォールバックも実行し、戻るボタンを2回押していた。「戻るが2段飛ぶバグ」を一瞬疑った。

### [UX] 自己レビューで拾った：広げた当たり判定が隣の「削除」に重なっていた
- 小さいボタンを見た目そのままで44pxにする `.hit-44`（`::after` で当たり判定だけ広げる）を、距離編集シートの隣り合うピンと削除にも付けていた。広げた範囲が互いに重なり、DOMで後ろにある削除の方が上に来るので、ピンの右端を押すと削除が反応しうる状態だった（取り消しを付けた直後だったのが救い）。
- 隣り合うボタンには `.hit-44` を使わず、実寸を40px幅にして負のマージンで行の高さを保つ形にした（4bdce78）。当たり判定を見た目より広げる手は、周りに押せるものが無い場所でだけ使う。
